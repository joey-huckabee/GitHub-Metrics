# GitHub-Metrics — Level 1 Requirements

## Purpose

This document establishes the Level 1 (L1) SHALL-statement requirements for
GitHub-Metrics: a maintained Python library and CLI that reads an inventory of
GitHub repositories and calculates metrics about them for free and open source
software analysis.

L1 requirements define **what** the product must do at the highest level of
abstraction. They are the root of the requirements tree; L2 requirements
decompose each L1 into architectural decisions, and L3 requirements decompose
each L2 into implementation-level obligations. All three levels are traced
through [`TRACE-MATRIX.md`](TRACE-MATRIX.md).

## Scope

This document covers the shipping Python package under `github_metrics/`.

The present release delivers **inventory ingestion**: reading and validating a
list of repositories. Metric collection over that inventory exists only as the
single-repository `repo` command inherited from the initial scaffolding, and
the batch pipeline that will consume an ingested inventory is deferred. Items
deferred to future releases are recorded in [`ROADMAP.md`](ROADMAP.md) rather
than here; items permanently out of scope are recorded under
**Non-Requirements** below.

## Conventions

### Requirement identifier format

Each L1 requirement carries a stable identifier of the form `L1-<CATEGORY>-<NNN>`,
where `<CATEGORY>` is a code from the table below and `<NNN>` is a zero-padded
sequence number within that category. Identifiers are permanent: a retired
requirement takes its identifier with it, and the number is never reused.

L2 and L3 requirements derived from an L1 use `L2-<CATEGORY>-<NNN>` and
`L3-<CATEGORY>-<NNN>`, with parent links recorded in their own documents and
resolved in the trace matrix.

Non-requirements use the prefix `NR-<NNN>`.

### SHALL language

Every requirement in this document uses SHALL to express a mandatory
obligation, per DO-178C and MIL-STD-498 convention. SHOULD, MAY and WILL are
reserved for L2/L3 derivations, where they carry their conventional meanings.

### Requirement metadata

Each requirement carries:

- **Statement** — the SHALL obligation itself.
- **Rationale** — why the requirement exists, for the benefit of a future
  maintainer who was not present for the decision.
- **Verification Method** — how compliance is demonstrated, drawn from the
  DO-178 vocabulary: Test (T), Analysis (A), Inspection (I), Demonstration (D).
  More than one may apply.
- **Evidence** — *optional*, and meaningful only for requirements verified
  without a test. It names the artifact that actually carries the check. A
  method on its own describes how a requirement *would* be verified; without
  evidence it is a plan rather than a result, and the trace matrix reports it
  as Draft.

**Status is not recorded in this file.** It is derived in
[`TRACE-MATRIX.md`](TRACE-MATRIX.md) from `@pytest.mark.requirement` markers in
`tests/` and the parent links in `L2.md` and `L3.md`, by
`scripts/build-trace-matrix.py`. This document carries specification content
only, so that nothing here can claim coverage the test suite does not provide.

### Verification method vocabulary

- **Test (T)** — executable verification. Implemented as pytest functions
  tagged `@pytest.mark.requirement("<id>")`.
- **Analysis (A)** — logical evaluation, including static analysis and
  reasoning about an implementation's structure. Recorded in
  [`ARCHITECTURE.md`](ARCHITECTURE.md) or an ADR under `adr/`.
- **Inspection (I)** — examination of code, documents or configuration.
  Recorded by citing the inspected artifact on the `**Evidence**` line.
- **Demonstration (D)** — operational observation of the running system by a
  human. Recorded as a procedure document.

## L1-ING: Repository inventory ingestion

### L1-ING-001

**Statement**: The system SHALL read an inventory of GitHub repositories from a
CSV file whose header names an `owner` column and a `repoid` column, where each
data row denotes the repository at `https://github.com/<owner>/<repoid>`.

**Rationale**: An inventory is the unit of work for FOSS analysis. Analysts
maintain these lists in spreadsheets and issue trackers, and CSV is the format
every such tool exports. Fixing the two column names, rather than accepting a
free-form URL column, keeps the input unambiguous: `owner` and `repoid` are
already the two identifiers the GitHub API is addressed by, so no parsing step
stands between the file and an API call.

**Verification Method**: Test (T)

### L1-ING-002

**Statement**: Ingestion SHALL perform no network access.

**Rationale**: Reading a list is separable from acting on it, and keeping the
separation strict has three consequences worth the constraint. A malformed
inventory is diagnosed in milliseconds rather than after a partial run has
already spent API quota; ingestion is testable without fixtures for the network
or credentials; and an analyst can check a list on a machine that has no GitHub
token at all. The cost is that ingestion cannot report whether a repository
actually exists — that is accepted, and stated in `RepositoryRef`.

**Verification Method**: Inspection (I)

**Evidence**: `github_metrics/ingest.py` imports no HTTP client, no `github`
module, and no socket API; `docs/ARCHITECTURE.md` records the layering.

### L1-ING-003

**Statement**: The system SHALL report every rejected row of an inventory
without abandoning the rows it can read, and SHALL additionally offer a mode
that abandons the read at the first rejection.

**Rationale**: The two modes serve genuinely different users. An analyst
cleaning a hand-maintained list needs the whole list of problems in one pass,
because fixing one row at a time across a hundred-row file is a hundred
edit-run cycles. An automated pipeline needs the opposite: any defect at all
should stop the run before downstream stages consume a partial inventory.
Serving only the first leaves pipelines silently processing incomplete data;
serving only the second makes the tool unusable for its primary audience.

**Verification Method**: Test (T)

## L1-VAL: Name validation

### L1-VAL-001

**Statement**: The system SHALL reject syntactically invalid GitHub account and
repository names during ingestion, and SHALL report the reason each name was
rejected.

**Rationale**: The common failure modes of a hand-maintained list are
mechanical: a pasted clone URL left whole in the `owner` column, a `.git`
suffix left on a repository name, a stray comment glued to a value. Every one
of them is cheap to catch by grammar and expensive to diagnose later, where it
arrives as one 404 among hundreds and is indistinguishable from a repository
that was deleted. Reporting the *reason* rather than a bare rejection is what
makes the report actionable without opening the file.

**Verification Method**: Test (T)

## L1-ERR: Error reporting and taxonomy

### L1-ERR-001

**Statement**: Every failure the system reports SHALL carry a stable identifier
that is documented in [`ERROR-CATALOG.md`](ERROR-CATALOG.md), and identifiers
SHALL NOT be reused once retired.

**Rationale**: Error text gets rewritten; identifiers do not. A stable code is
what lets a log line, a support conversation and a runbook entry written two
years apart refer to the same condition, and what lets a pipeline branch on a
specific failure without pattern-matching prose that the next release may
reword.

**Verification Method**: Test (T), Inspection (I)

---

## L1-CON: Concurrency

### L1-CON-001

**Statement**: The system SHALL read multiple inventory files concurrently, and
SHALL produce results that do not depend on the order in which those reads
complete.

**Rationale**: Concurrency is worth having here because inventories arrive as
sets of files and the work is I/O bound. It is only worth having if the answer
is stable: an inventory whose order changes between runs cannot be diffed,
reviewed, or used as a reproducible input to an analysis. Determinism is
therefore part of the requirement rather than a quality attribute of it.

**Verification Method**: Test (T)

---

## L1-CLI: CLI capability surface

### L1-CLI-001

**Statement**: The system SHALL expose ingestion through the command line with
both human-readable and machine-readable output, and SHALL distinguish by exit
status between a clean read, a read that rejected rows, and an input that could
not be read at all.

**Rationale**: The command is used interactively by analysts and
non-interactively by pipelines, and those two audiences need different things
from the same run. Three exit statuses rather than two exist because "the file
loaded but eleven rows need fixing" is an operational state distinct from both
success and failure, and a pipeline should be able to act on it without parsing
the report.

**Verification Method**: Test (T)

---

## L1-LOG: Diagnostic logging

### L1-LOG-001

**Statement**: The system SHALL emit diagnostics on a stream separate from its
data output, at a severity the operator can select.

**Rationale**: The CLI writes JSON to standard output. A log line interleaved
into that stream corrupts it for every downstream consumer, so diagnostics go
to standard error. Severity is selectable because the per-row detail that makes
a broken inventory diagnosable is noise on a healthy one.

**Verification Method**: Test (T)

---

## L1-OUT: Result output and destinations

### L1-OUT-001

**Statement**: The system SHALL emit results as CSV, as JSON, and as a console
rendering, all three carrying the same column set in the same order.

**Rationale**: The three forms serve a pipeline, a program, and a person, and
all three are reading the same measurements. If the formats can disagree about
which columns exist or what order they are in, a consumer that switches between
them has to maintain a mapping — and the mapping is where the drift hides. One
definition, three renderings.

**Verification Method**: Test (T)

### L1-OUT-002

**Statement**: The caller SHALL be able to select which columns are emitted,
and selecting none SHALL emit all of them.

**Rationale**: Not every consumer wants nineteen columns, and on this tool the
selection is not merely cosmetic: a column nobody asked for needs no data, so
the selection also determines which API calls a run must make. That makes it a
rate-limit lever. Defaulting to everything keeps the common case free of
ceremony.

**Verification Method**: Test (T)

### L1-OUT-003

**Statement**: A value that was not collected SHALL be distinguishable in every
output format from a value that was collected and is zero.

**Rationale**: Zero is a legitimate measurement — a repository really can have
no releases and no closed issues. Writing zero for "not known" would make a
measured repository indistinguishable from one that could not be read, and
every aggregate computed downstream would silently include the difference.
This is why an unfetchable repository still produces a row: the row is the
record that the repository was asked about, and the empty cells are the record
that no answer came back.

**Verification Method**: Test (T)

## L1-MET: Metric collection

### L1-MET-001

**Statement**: A collected value SHALL measure what its column name denotes,
and SHALL be obtained by the cheapest API route that returns a correct value.

**Rationale**: A number that measures something adjacent to its name is worse
than no number, because it is still comparable, still plottable, and still
wrong. Closed issues is the case in point: the REST route counts pull requests
as issues, which for a typical repository roughly triples the figure. Cost is
part of the same requirement rather than a separate concern, because an
inventory of four hundred repositories only completes if the per-repository
request cost fits inside the token's hourly budget.

**Verification Method**: Test (T)

### L1-MET-002

**Statement**: A metric SHALL distinguish a value that is genuinely zero from
a value that is unavailable or inapplicable.

**Rationale**: Zero is a legitimate measurement, so it cannot double as "not
known". A repository with its issue tracker disabled reports zero closed
issues, but that is a fact about its configuration rather than about its
maintenance, and scoring the two identically would penalise a project that
tracks its work elsewhere.

**Verification Method**: Test (T)

---

## L1-SCR: Scoring

### L1-SCR-001

**Statement**: Every score component SHALL be a pure, total function of its
documented input, and its bands SHALL be published.

**Rationale**: Purity is what makes a band table testable across its whole
domain without a network or a token; totality is what stops an input falling
between two branches. Both were violated in the implementation this replaces,
silently and in three separate ways. Publishing the bands is what makes a score
interpretable: a number between 0 and 1 with no visible thresholds cannot be
argued with or acted on.

**Verification Method**: Test (T)

---

## L1-TRU: Trust policy

### L1-TRU-001

**Statement**: The set of owners treated as trusted SHALL be an explicit,
documented input that a caller can replace, and SHALL NOT be inferred from
anything the GitHub API reports.

**Rationale**: Every other value in the output is a measurement; this one is a
judgement about which institutions the analysis trusts. It cannot be derived
from GitHub - the API reports `spring-projects` as "Spring" and its `company`
field as null, while the judgement being recorded is that VMware stands behind
it. Because it is policy rather than fact, an analysis that trusts a different
set of institutions is a different analysis rather than a different program,
and the list has to be replaceable without editing source.

**Verification Method**: Test (T)

## Non-Requirements

These are explicitly out of scope. They are recorded so that a future reader
can tell a deliberate omission from an oversight.

### NR-001 — Existence checking during ingestion

Ingestion does not confirm that a repository exists, is public, or is
reachable. Doing so requires the network access L1-ING-002 forbids. A
syntactically valid reference is a *plausible* repository and nothing more.

### NR-002 — Input formats other than CSV

JSON, YAML, TOML and newline-delimited URL lists are not accepted. CSV is what
the tools analysts already use export, and every additional format is another
parser to keep correct against the same corner cases.

### NR-003 — Deriving `owner`/`repoid` from a URL column

An inventory naming repositories by URL is not accepted. URL parsing invites
ambiguity that the two-column form does not have — `git@`, `https://`, trailing
`.git`, embedded credentials, enterprise hosts — and the two-column form is
trivially produced from URLs by the person who has them.

### NR-004 — Process-level parallelism

Ingestion uses threads, not processes. The work is I/O bound, so a process pool
would add serialisation cost and startup latency without removing a bottleneck.
See [`adr/0002-concurrency-across-files-not-within-a-file.md`](adr/0002-concurrency-across-files-not-within-a-file.md).

### NR-005 — Mutating the input file

The tool never rewrites, deduplicates in place, or otherwise edits an inventory
it was given. The input is the analyst's document; the tool reports on it.
