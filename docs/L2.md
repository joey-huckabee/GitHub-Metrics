# GitHub-Metrics — Level 2 Requirements

## Purpose

This document establishes the Level 2 (L2) SHALL-statement requirements for
GitHub-Metrics. L2 requirements are architectural derivations of the L1
requirements in [`L1.md`](L1.md): they specify *how* each L1 obligation is
structurally satisfied, without yet prescribing implementation detail, which
belongs to [`L3.md`](L3.md).

Every L2 requirement traces to exactly one L1 parent via its `**Parent**:`
field. Where an L2 is motivated by more than one L1, the primary parent is
declared and the supporting obligations are named in prose.

## Conventions

L2 identifiers follow `L2-<CATEGORY>-<NNN>`. Metadata fields carry the same
semantics as in [`L1.md`](L1.md), including the rule that an `**Evidence**`
line is required before a non-Test verification method can count as satisfied.

Numbering is monotone within a category; gaps are retired identifiers and are
never reused.

**Status is not recorded here.** It is derived in
[`TRACE-MATRIX.md`](TRACE-MATRIX.md) by `scripts/build-trace-matrix.py`.

## L2-ING: Repository inventory ingestion

#### L2-ING-001

**Parent**: L1-ING-001
**Statement**: Ingestion SHALL yield, for each accepted data row, a value
carrying the row's `owner`, its `repoid`, and the 1-based source line the row
occupied.
**Rationale**: The source line is what makes a later failure traceable to the
row that requested it. Without it, a 404 arriving during collection can be
attributed to a repository name but not to a position in the analyst's file,
which is the thing they have to edit.
**Verification Method**: Test (T)

#### L2-ING-002

**Parent**: L1-ING-001
**Statement**: Ingestion SHALL accept a file that begins with a UTF-8
byte-order mark.
**Rationale**: "Save as CSV UTF-8" in Excel on Windows writes a BOM, and that
is the single most common way an analyst produces one of these files. Without
explicit handling the first header cell arrives as `﻿owner`, the header
match fails, and the tool reports a missing `owner` column against a file whose
first line visibly says `owner`. The diagnostic would be actively misleading.
**Verification Method**: Test (T)

#### L2-ING-003

**Parent**: L1-ING-001
**Statement**: Ingestion SHALL accept both LF and CRLF line endings.
**Rationale**: The inventory is authored on whichever platform the analyst
uses, and is frequently mailed between platforms. Line endings carry no meaning
here, so they must not be able to change the result.
**Verification Method**: Test (T)

#### L2-ING-004

**Parent**: L1-ING-001
**Statement**: Header matching SHALL be insensitive to case, to surrounding
whitespace, and to column order, and SHALL ignore columns it does not
recognise.
**Rationale**: These files are maintained by hand and by spreadsheet. Rejecting
`Owner` or ` repoid ` would fail on cosmetic differences that carry no meaning.
Ignoring unknown columns matters more: an analyst's real inventory carries
bookkeeping the tool has no interest in — a steward, a review date, a
priority — and a tool that refused such a file would force them to maintain a
second copy of the list.
**Verification Method**: Test (T)

#### L2-ING-005

**Parent**: L1-ING-001
**Statement**: Ingestion SHALL skip rows that carry no content and SHALL strip
surrounding whitespace from the values it reads.
**Rationale**: A trailing newline, a blank separator line and a final `,,` row
are artifacts of how the file was written, not statements about the data.
Reporting them as errors would fill a report with noise that the analyst can
neither act on nor prevent.
**Verification Method**: Test (T)

#### L2-ING-006

**Parent**: L1-ING-003
**Statement**: Ingestion SHALL treat two rows as naming the same repository
when their owner and repoid match case-insensitively, SHALL keep the first
occurrence, and SHALL report each subsequent one against the line of the first.
**Rationale**: GitHub resolves account and repository names case-insensitively,
so `PyPA/virtualenv` and `pypa/virtualenv` are one repository. Collecting both
would double-count it in every aggregate the analysis produces. Keeping the
first occurrence rather than the last makes the result independent of where in
the file the duplicate was added, and naming the earlier line is what lets the
analyst find the pair.
**Verification Method**: Test (T)

#### L2-ING-007

**Parent**: L1-ING-001
**Statement**: Ingestion SHALL apply CSV quoting rules, and SHALL read
inventories of at least several thousand rows without special handling by the
caller.
**Rationale**: A quoted field containing a separator must stay one cell;
mis-parsing it would shift every subsequent column silently, which is worse
than any loud failure. The scale figure reflects the real upper bound of a
curated FOSS inventory and is stated so that the deliberate choice to hold the
file in memory is bounded by something rather than assumed.
**Verification Method**: Test (T)

#### L2-ING-008

**Parent**: L1-ING-002
**Statement**: The ingestion module SHALL depend on no HTTP client, no GitHub
API client, and no socket interface.
**Rationale**: L1-ING-002 is a property of the dependency graph, not of any
single execution. A test can only show that one particular run made no request;
inspecting the imports shows that no run can.
**Verification Method**: Inspection (I)
**Evidence**: `github_metrics/sources/csv_inventory.py` — its import list contains no HTTP
client, no GitHub API client and no socket interface, and its two sibling
imports are themselves network-free; the layering is recorded in
`docs/ARCHITECTURE.md`.

#### L2-SRC-001

**Parent**: L1-ING-004
**Statement**: A written reference SHALL be reduced to `owner` and `repoid`
from a slug or from any usual GitHub URL, and a URL naming a host other than
GitHub SHALL be refused rather than reduced.
**Rationale**: The URL forms in circulation all name the same thing: with and
without a scheme, with `www.`, with a trailing slash, with `.git`, with the
`git@` clone form, and with whatever path was left over from browsing the
issues. Handling them is cheap and refusing them is a technicality.

The host is where leniency stops. `gitlab.com/foo/bar` reduces perfectly well
to `foo/bar`, which is exactly the problem: the result is a plausible reference
to a different repository that may well exist, so a mistake would become a row
rather than an error. GitHub Enterprise is served by naming the repository as a
slug, which is unambiguous.
**Verification Method**: Test (T)

#### L2-SRC-002

**Parent**: L1-ING-004
**Statement**: Whether an argument is a path or a repository SHALL be decided
by rules applied in a fixed order, and the order SHALL be documented.
**Rationale**: The two forms overlap — `data/inventory.csv` and
`pypa/virtualenv` are both a word, a slash and a word — so something has to
decide, and a decision a user cannot predict is worse than a restriction they
can. URL first, then an existing file, then a `.csv` suffix, then a slug. The
suffix rule earns its place by diagnosis: without it a mistyped path is read as
a slug and refused for having no `/`, which is true and useless, instead of
reporting the missing file.

The cost is that a repository whose name ends in `.csv` has to be given as a
URL. That is a real limitation, and it is preferable to a rule that guesses.
**Verification Method**: Test (T)

#### L2-SRC-003

**Parent**: L1-CON-001
**Statement**: A repository named more than once across the sources of one run
SHALL be collected once, and the repetition SHALL be reported against the
source that named it first.
**Rationale**: Within a file this already happens. Across files it cannot, and
the consequence is not cosmetic: the same repository collected twice spends the
rate limit twice and produces two identical rows that no consumer can
distinguish from a genuine duplicate in the inventory. Keeping the first
mention rather than the last is what stops a repetition from changing the
output order, which is the property input order exists to provide.
**Verification Method**: Test (T)

## L2-VAL: Name validation

#### L2-VAL-001

**Parent**: L1-VAL-001
**Statement**: An account name SHALL be accepted only when it consists of
letters, digits and hyphens, is no longer than 39 characters, and neither
begins with, ends with, nor contains consecutive hyphens.
**Rationale**: This is the grammar github.com enforces at sign-up. Accepting
anything wider defers a rejection the tool could have made instantly to a 404
it cannot explain.
**Verification Method**: Test (T)

#### L2-VAL-002

**Parent**: L1-VAL-001
**Statement**: A repository name SHALL be accepted only when it consists of
letters, digits, hyphens, underscores and dots, is no longer than 100
characters, is neither `.` nor `..`, and does not end in `.git`.
**Rationale**: Again the grammar github.com enforces. The `.git` exclusion
earns its own clause because of how these lists get built: pasting clone URLs
and stripping the host leaves the suffix behind, and GitHub rejects such a
name. The rule targets the *suffix* only — a repository legitimately named
`gitignore` or `dot.git.files` must survive.
**Verification Method**: Test (T)

#### L2-VAL-003

**Parent**: L1-VAL-001
**Statement**: Validation SHALL return the reason a name was rejected rather
than a bare success or failure.
**Rationale**: The reason is what the error catalog distinguishes on, and what
makes a report actionable without opening the file. Recovering "too long" from
"illegal character" after the fact would mean inspecting the value a second
time, in a second place, with the rules written twice.
**Verification Method**: Test (T)

## L2-ERR: Error reporting and taxonomy

#### L2-ERR-001

**Parent**: L1-ERR-001
**Statement**: A condition that makes a whole file unusable SHALL raise a typed
exception carrying its documented code.
**Rationale**: There is no partial result to return when the header is
unreadable or the bytes are not text. Raising, rather than returning an empty
result, prevents a caller from mistaking "this file is broken" for "this file
is empty".
**Verification Method**: Test (T)

#### L2-ERR-002

**Parent**: L1-ERR-001
**Statement**: A condition that spoils one row SHALL be recorded as data on the
result, carrying its code, its 1-based physical line number, and a message
naming the offending value.
**Rationale**: Row problems are the normal state of a hand-maintained
inventory, not an exceptional one. Modelling them as data rather than as
control flow is what allows every one of them to be reported in a single pass.
The line number is physical rather than logical so that it matches what the
analyst's editor shows.
**Verification Method**: Test (T)

#### L2-ERR-003

**Parent**: L1-ING-003
**Statement**: In strict mode the first row-level issue SHALL be raised as an
exception naming that issue, and no result SHALL be returned.
**Rationale**: A pipeline that opts into strict mode wants the run stopped, and
wants to know which row stopped it. Returning a partial result alongside the
error would leave a caller able to use it by accident.
**Verification Method**: Test (T)

#### L2-ERR-004

**Parent**: L1-ERR-001
**Statement**: Every error this package raises deliberately SHALL derive from a
single base class, and every code SHALL be unique within the taxonomy.
**Rationale**: One base class lets a caller catch "any problem this tool
reports" with one `except` while leaving genuine bugs — a `TypeError` from a
mistake in our own code — free to propagate. Uniqueness is what makes a code
usable as an identifier at all.
**Verification Method**: Test (T)

## L2-CON: Concurrency

#### L2-CON-001

**Parent**: L1-CON-001
**Statement**: Multiple inventory files SHALL be read on a bounded thread pool,
with the bound defaulting to the smaller of the file count and a fixed ceiling.
**Rationale**: The work is dominated by waiting on storage, which threads
overlap well. The ceiling exists because the benefit stops early: past a
handful of concurrent reads the device, not the waiting, is the limit, and a
thread per file would be pure overhead for a directory of hundreds.
**Verification Method**: Test (T)

#### L2-CON-002

**Parent**: L1-CON-001
**Statement**: Results SHALL be returned in the order the sources were
supplied, and when more than one source fails, the error reported SHALL be the
one belonging to the earliest source in that order.
**Rationale**: Both halves are about the same failure. Completion order varies
run to run, so anything derived from it varies too — an inventory that reorders
itself is not diffable, and an error that changes identity between runs cannot
be written into a runbook. Ordering results is the obvious half; ordering
*errors* is the half that is easy to miss and that only shows up once a batch
contains two bad files.
**Verification Method**: Test (T)

#### L2-CON-003

**Parent**: L1-CON-001
**Statement**: The number of worker threads SHALL NOT change the result of a
read, and parsing within a single file SHALL remain sequential.
**Rationale**: A worker count that changes the answer is a race, so this is
stated as an obligation rather than assumed. Parsing stays sequential because
the phases within one file are genuinely dependent — the header determines
column positions, and duplicate detection depends on what came before — and the
per-row work is small enough that coordination would cost more than it saves.
See [`adr/0002-concurrency-across-files-not-within-a-file.md`](adr/0002-concurrency-across-files-not-within-a-file.md).
**Verification Method**: Test (T)

#### L2-SCR-003

**Parent**: L1-SCR-001
**Statement**: A composite score SHALL combine its components so that the
result is non-decreasing in every component, and SHALL NOT select between them
on a threshold of one component's value.
**Rationale**: Selecting on `closed_issues == 0` put a cliff at exactly one
closed issue - a project scored 20.0 with none and 2.0 with one. Taking the
stronger signal removes the cliff and the branch together, and makes the
guarantee checkable: closing an issue or cutting a release can never lower a
project's score.
**Verification Method**: Test (T)

#### L2-SCR-004

**Parent**: L1-MET-002
**Statement**: A signal that is unavailable SHALL be excluded from a composite
score rather than scored at its minimum.
**Rationale**: A repository with its issue tracker disabled has no issue
signal, and neither does one with nothing closed in it. Neither is the same as
a low signal. The closed-issue table floors at 0.1 for any count below 20,
zero included, so scoring an absent signal at that floor would place a project
with no evidence at all above one with none - backwards. Both absences are
therefore excluded rather than floored.
**Verification Method**: Test (T)

## L2-CLI: CLI capability surface

#### L2-CLI-001

**Parent**: L1-CLI-001
**Statement**: The CLI SHALL provide a `validate` subcommand accepting one or
more source paths and reporting the repositories read from each.
**Rationale**: Accepting several paths in one invocation is what makes the
concurrency of L2-CON-001 reachable from the command line at all.
**Verification Method**: Test (T)

#### L2-CLI-002

**Parent**: L1-CLI-001
**Statement**: The `validate` subcommand SHALL run without a configured GitHub
token.
**Rationale**: L1-ING-002 makes ingestion network-free, and a command that
needs no credential must not demand one. This constrains the CLI's structure:
configuration that requires a token cannot be resolved when the command group
starts, only when a command that needs it runs.
**Verification Method**: Test (T)

#### L2-CLI-003

**Parent**: L1-CLI-001
**Statement**: The `validate` subcommand SHALL offer a machine-readable output
format on standard output, uncontaminated by diagnostics, and SHALL be able to
write its report to a file.
**Rationale**: The machine-readable form is the handoff to whatever consumes
the inventory next. It is only usable if nothing else shares the stream, which
is what ties this requirement to L1-LOG-001.
**Verification Method**: Test (T)

#### L2-CLI-004

**Parent**: L1-CLI-001
**Statement**: The `validate` subcommand SHALL exit 0 when every row was
accepted, 3 when the sources were read but at least one row was rejected, and 2
when a source could not be read.
**Rationale**: The middle status is the point. Collapsing it into success hides
a degraded inventory from any pipeline that only checks for zero; collapsing it
into failure discards a result that is usually still worth having.
**Verification Method**: Test (T)

#### L2-CLI-006

**Parent**: L1-SCR-001
**Statement**: Every band table SHALL be printable from the command line
without credentials and without network access, rendered from the same tables
the scoring code reads.
**Rationale**: L1-SCR-001 requires the bands to be published; a table
transcribed into a document is published only until someone edits the code.
Rendering from the object itself removes the possibility of disagreement. The
no-credentials part is what makes reviewing the model a thing you can do before
deciding a collection run is worth its quota, and it is also the mechanism that
gives every `describe_bands` a caller - three of the five had none, which is
the same defect that reached review once already.
**Verification Method**: Test (T)

#### L2-CLI-007

**Parent**: L1-CLI-001
**Statement**: Collection SHALL be reachable as a single command taking the
same sources as validation, and that command SHALL produce every artifact of a
run under one scan identity, with no flag governing which artifacts are
written.
**Rationale**: One command, one run, one identity. The alternative shapes were
all worse in the same way.

Two commands - `scan` for the table and `contributors` for the documents -
was the previous answer, and it was made on cost: `scan` would never pay for
contributor pages. It does not survive the observation that a document *is*
the row plus a contributor block. Two commands produce two `scan_id` values
and two `scan_date` values, so the two halves of one measurement cannot be
rejoined afterwards, which is the only thing those columns exist for.

Flags selecting which artifacts to write were considered and rejected. They
buy one state that nothing else expresses - documents without a table - and
in exchange every invocation has to be read to know what a run produced. They
would also not be the cost lever they appear to be: the repository query
returns every column of a row for one point whether or not a document is
written, so the artifact selection saves nothing on the metrics side.

The cost is accepted rather than hidden: every run now pays for contributor
pages and for geocoding, and `L2-COL-003` covers the budget that must hold.

Two command names are retired by this and neither is reused. `repo` was
scaffolding collecting a different field set; `metrics` became `scan` so the
command and the `scan_id` it stamps share a word; `contributors` folded in
here.

**Verification Method**: Test (T)

### Retired

Identifiers are permanent: a retired requirement keeps its number, the number
is never reused, and what it required is recorded here rather than deleted.

- **L2-CLI-005** — *Each metric shall be reachable from the command line on
  its own, reporting the collected value, the score it produces, and on
  request the bands that produced it.* **Retired in v0.3.0.** The requirement
  existed so that a metric definition could be checked against real
  repositories while it was still being argued about; every definition in
  `METRICS.md` now reads Settled, so the condition that justified it no longer
  holds. What survives it is `L2-CLI-006`, which keeps the band tables
  printable without a token — that was the half of the probe commands still
  being used, and it is a command of its own.

  The collectors the probes drove (`collect.closed_issues`,
  `collect.releases`) are kept as library API rather than deleted. They are
  reachable from `github_metrics`, they are tested, and `L2-MET-001` through
  `L2-MET-007` still describe them.

## L2-LOG: Diagnostic logging

#### L2-LOG-001

**Parent**: L1-LOG-001
**Statement**: Row-level issues SHALL be logged at DEBUG and per-file outcomes
at INFO, on standard error.
**Rationale**: The severities match who needs them. A per-file summary is
useful on every run; per-row detail is only useful when something is wrong, and
would otherwise bury the summary. Standard error keeps both off the stream
carrying the machine-readable report.
**Verification Method**: Test (T)

#### L2-LOG-002

**Parent**: L1-LOG-001
**Statement**: Collection and scoring SHALL log per-repository detail at DEBUG.
INFO SHALL carry per-run outcomes only, and a condition needing attention SHALL
be a WARNING.
**Rationale**: The unit of work is the repository, and an inventory holds
hundreds of them. Anything narrated per repository at INFO is multiplied by the
size of the inventory, so a run of four hundred buries whatever the operator
actually needed to see under thousands of lines that only matter when a
specific number is being questioned — which is what DEBUG is for. The
severities carry the volume, not the interest: a value worth explaining is
DEBUG, a value worth doubting is a WARNING.
**Verification Method**: Test (T)

#### L2-LOG-003

**Parent**: L1-LOG-001
**Statement**: Diagnostics SHALL be written to standard error by default, at a
level selected from the environment, configured exactly once per process; a
module SHALL name a logger and never configure one.
**Rationale**: L2-LOG-001 and L2-LOG-002 derive which severity carries what.
This derives the other half of L1-LOG-001, which nothing else did: the stream
and the selection.

Standard error rather than standard output, because the CLI writes JSON to
stdout and one interleaved log line corrupts it for every downstream consumer.
Once per process, because two handlers on one logger duplicate every record.
And configuration in one module because a library that configures logging on
import takes the decision away from the program embedding it - modules name a
logger with `getLogger(__name__)` and nothing else.
**Verification Method**: Test (T)

#### L2-COL-001

**Parent**: L1-OUT-001
**Statement**: Every reference SHALL produce an outcome, and a repository that
cannot be collected SHALL NOT prevent the collection of any other.
**Rationale**: The output has one row per accepted input row, so a reference
that fails still occupies a position. Letting the failure propagate would
abandon the repositories after it and discard the ones already paid for, which
turns one bad entry in a four-hundred-row inventory into a wasted run.

**Verification Method**: Test (T)

#### L2-COL-002

**Parent**: L1-CON-001
**Statement**: Collection SHALL be concurrent across repositories and SHALL
return results in input order.
**Rationale**: The work is a network round trip per repository, which is what
threads overlap well. The pool is small because the constraint is the rate
limit rather than the processor, and because a large pool turns a token's
budget into a burst GitHub is entitled to refuse.

Input order is a requirement rather than a quality attribute: these files are
compared against earlier runs, so a diff has to show changed data rather than
reordered rows. `Executor.map` gives that; `as_completed` would not, and the
difference is invisible until a run happens to complete out of order.

**Verification Method**: Test (T)

#### L2-COL-003

**Parent**: L1-MET-001
**Statement**: A run SHALL confirm the token's remaining budget covers it
before collecting anything, and SHALL refuse to start when it does not.
**Rationale**: Collection costs one point per repository, so this is a
comparison rather than an estimate. A run that discovers exhaustion halfway has
already spent what it had and produced a file that is part measurement and part
absence, with nothing to distinguish the two: the repositories at the end of
the inventory look exactly like repositories that could not be read. Refusing
costs one request that does not count against the limit, and leaves the quota
intact for a smaller run.

No reserve is held back. The budget runs to zero, so a full hourly quota
collects exactly 5,000 repositories, which is the largest run the tool can do.
Holding points back would refuse a run the token could actually have finished,
which is the wrong trade for a tool whose job is the batch.

**Verification Method**: Test (T)

#### L2-ROW-001

**Parent**: L1-OUT-001
**Statement**: The assembly of a collected repository into an output row SHALL
happen in exactly one place.
**Rationale**: This is the join between the two halves of the tool, and it is
the seam where the structural rule would be broken first. Spreading it across
the collectors would put scoring inside collection; spreading it across the
renderers would put it after the point where a row is supposed to be finished.
One place is also what makes the reference row in `METRICS.md` testable end to
end.

**Verification Method**: Test (T)

#### L2-ROW-002

**Parent**: L1-MET-002
**Statement**: A repository that could not be collected SHALL produce a row
carrying what is known without the API, with every measurement and every score
empty rather than zero.
**Rationale**: Zero is a legitimate score for a repository that was measured
and found wanting. Using it for a repository that could not be read would put
the two in one bucket, and every average over the file would absorb the
difference silently. Empty says nothing was measured, which is the fact.

The identity columns are filled because they never needed the API, and because
a row that cannot say which repository it describes is not a row.

**Verification Method**: Test (T)

## L2-OUT: Result output and destinations

#### L2-OUT-001

**Parent**: L1-OUT-001
**Statement**: The column set and its order SHALL be derived from a single type
definition, and every output format SHALL take its columns from it.
**Rationale**: A second, hand-maintained list of column names is the mechanism
by which formats drift apart. Deriving the header from the type means a field
cannot be added without appearing in the output, and cannot appear in one
format but not another.
**Verification Method**: Test (T)

#### L2-OUT-002

**Parent**: L1-OUT-001
**Statement**: CSV output SHALL write a header even when there are no rows,
SHALL preserve the order of the rows it is given, and SHALL use LF line
endings.
**Rationale**: A header-only file is well-formed and says "no repositories",
which a zero-byte file does not - a consumer cannot tell that from a failed
run. Row order is the caller's, because the input order is the analyst's order.
LF because the file is a data interchange artifact and this repository is LF
throughout.
**Verification Method**: Test (T)

#### L2-OUT-003

**Parent**: L1-OUT-001
**Statement**: JSON output SHALL be an array of objects keyed by the column
names, SHALL preserve JSON-native types for numbers and booleans, and SHALL
repeat the run identity in every object.
**Rationale**: Stringifying a number that JSON can represent forces every
consumer to re-parse it, and re-parsing is where a locale or precision bug
enters. The identity repeats rather than being hoisted to the top level so that
the JSON and the CSV carry the same information in the same shape, and moving
between them needs no mapping layer.
**Verification Method**: Test (T)

#### L2-OUT-004

**Parent**: L1-OUT-001
**Statement**: Console output SHALL render each row as a vertical block of
label and value, separated from the next.
**Rationale**: Twenty columns do not fit across a terminal. A horizontal
table would wrap or truncate, and a truncated metric is worse than an absent
one because it still looks like a number.
**Verification Method**: Test (T)

#### L2-OUT-005

**Parent**: L1-OUT-002
**Statement**: A field selection SHALL be returned in canonical column order
regardless of the order given, SHALL ignore case and surrounding whitespace,
and SHALL collapse duplicates.
**Rationale**: Two runs asking for the same columns must produce byte-identical
headers, so that a diff between their outputs shows changed data rather than
reordered columns. The tolerances exist because these names are typed by hand
on a command line, where a repeated or padded name expresses the same intent as
a clean one.
**Verification Method**: Test (T)

#### L2-OUT-006

**Parent**: L1-OUT-002
**Statement**: An unrecognised field name SHALL be rejected with its documented
code and, where one exists, the closest matching valid name.
**Rationale**: Silently ignoring an unknown name would produce output missing a
column the caller believed they had asked for, which is discovered much later
and blamed on the data. The suggestion exists because the failure mode is a
typo, and naming the near miss saves a trip to the documentation.
**Verification Method**: Test (T)

#### L2-OUT-007

**Parent**: L1-OUT-003
**Statement**: An uncollected value SHALL render as an empty field in CSV and
as `null` in JSON; booleans SHALL render lowercase; floats SHALL render at full
precision.
**Rationale**: Empty and `null` are each format's own way of saying "no value",
so neither can be confused with zero. Lowercase booleans match the agreed
output. Full precision because these are measurements, and rounding at the
output boundary discards resolution the caller may need without telling them.
**Verification Method**: Test (T)

#### L2-OUT-008

**Parent**: L1-OUT-001
**Statement**: When a destination names an existing directory the default
filename SHALL be used inside it; when no destination is given output SHALL go
to the console; and an unwritable destination SHALL be reported before
collection begins.
**Rationale**: The three cases match how a caller thinks about it - "this
file", "this directory, you pick the name", and "just show me". Validating the
destination early matters because the alternative is discovering it after a run
has spent its API budget, and that budget does not refill for an hour.
**Verification Method**: Test (T)

#### L2-OUT-009

**Parent**: L1-OUT-001
**Statement**: The run identity SHALL be generated once per run, SHALL be
timezone-aware, and SHALL stamp every row including rows for repositories that
could not be read.
**Rationale**: Per-run rather than per-repository is what makes a result set
groupable once it is stored. Timezone-aware because a naive timestamp is
ambiguous the moment it leaves the machine that made it, and these values are
written to files and later to a database. Unreadable rows are stamped too,
because a row that cannot be attributed to a run is of little use in either.
**Verification Method**: Test (T)

#### L2-OUT-010

**Parent**: L1-OUT-004
**Statement**: A per-repository document SHALL be written at
`<root>/<owner>/<repoid>.json`, lower-cased throughout, and SHALL be absent
for any repository that was not fully collected.
**Rationale**: Three decisions, each rejecting something that looks reasonable.

**Nested rather than flattened.** `<owner>-<repoid>.json` silently loses
repositories: hyphens are legal in both an account name and a repository name,
so `foo-bar/baz` and `foo/bar-baz` map onto one file. They are two different
repositories rather than a duplicate pair, so the duplicate detection that
guards an inventory reports nothing, one file overwrites the other, and the
run exits clean with a repository missing. A path separator is not legal in
either name, so nesting removes the collision by construction instead of
detecting it.

**Lower case.** GitHub names are case-insensitive and `RepositoryRef.key`
already folds case to say so, so a case-sensitive path would contradict the
tool's own notion of identity - two files for one repository on Linux, and a
silent overwrite reported as two successes on Windows and macOS.

**Absent rather than empty.** See L1-OUT-004.

**Verification Method**: Test (T)

#### L2-OUT-011

**Parent**: L1-OUT-004
**Statement**: A document SHALL carry every column of the tabular row, under
the same names and in the same order and complete, followed by the contributor
block; the block's keys SHALL NOT be columns of the tabular row; and field
selection SHALL NOT apply to a document.
**Rationale**: Same names and same order is what lets the two artifacts join
without a translation table, and stating it as "the columns, complete, then a
fixed suffix" is a rule a test can check in one line - which the previous
formulation, "the first twenty keys must not collide with the rest", could not.

The block's keys belong to the document because the document is what carries
contributor detail; the tabular row is the comparable record and its shape is
fixed so that two runs diff and a column sorts. Keeping the block out of the
row is also what lets `contribution_total` be a plain number: a document exists
only where the contributor list was read, so a zero there always means the list
was read and was empty.

Field selection is excluded because it is a rendering convenience for a
tabular file. A document with columns missing would stop being the row, and
the pair would lose the one property it exists to have.

**Verification Method**: Test (T)

## L2-MET: Metric collection

#### L2-MET-001

**Parent**: L1-MET-001
**Statement**: The closed-issue count SHALL exclude pull requests.
**Rationale**: GitHub models pull requests as issues in its REST API, so the
issues endpoint returns both and offers no server-side filter. For
`cline/cline` that is 3,770 closed issues against 7,001 closed pull requests -
a count including both measures development throughput, not issue triage, and
the column is named for the latter.
**Verification Method**: Test (T)

#### L2-MET-002

**Parent**: L1-MET-001
**Statement**: Counts SHALL be obtained through GraphQL, requesting totals
rather than nodes, at a cost of one point per repository.
**Rationale**: REST cannot answer the question correctly at any price. Its
repository object carries no closed-issue count; its issues endpoint includes
pull requests; and since GitHub moved that endpoint to cursor pagination the
responses no longer carry `rel="last"`, so any total derived from the last-page
link now reads 1 for every repository. GraphQL returns an exact total, excludes
pull requests by construction, and costs one point of 5,000 per hour.
Requesting `nodes` rather than `totalCount` would page through every issue and
make the cost proportional to the repository's history.
**Verification Method**: Test (T)

#### L2-MET-003

**Parent**: L1-MET-001
**Statement**: GraphQL errors SHALL be detected and classified, with an absent
repository distinguished from every other failure.
**Rationale**: GraphQL reports failure with HTTP 200 and an `errors` array, so
a caller checking only the status code sees success and then reads a null
repository. The distinction matters downstream: a deleted, renamed or private
repository is an expected outcome of a syntactically valid reference and
produces a row with empty metrics, whereas a malformed query is a defect in
this program.
**Verification Method**: Test (T)

#### L2-MET-004

**Parent**: L1-MET-002
**Statement**: Whether a repository's issue tracker is enabled SHALL be
collected alongside the counts, and a disabled tracker SHALL be reported.
**Rationale**: Without the flag, a disabled tracker and an unused one are the
same zero. Collecting it costs nothing - it is a field in a query already being
made - and it is the only way a later reader can tell why the count is zero.
**Verification Method**: Test (T)

#### L2-MET-005

**Parent**: L1-MET-001
**Statement**: Release and tag counts SHALL be collected as two separate
values in one query.
**Rationale**: They answer different questions - whether a project publishes
formal artifacts, and how many versions it has cut - and the relationship
between them is what the scored value depends on. Collecting only their sum
discards it irrecoverably. Both are fields of a query already being made, so
keeping them apart costs nothing.
**Verification Method**: Test (T)

#### L2-MET-006

**Parent**: L1-MET-001
**Statement**: The count of versions SHALL count each version once.
**Rationale**: Creating a GitHub Release requires a tag, so releases are a
subset of tags - measured across five repositories, the number of release tag
names absent from the tag list was zero every time. Adding the two therefore
counts every release twice. The inflation is not a constant factor either: it
ranges from 1.00x for a project that only tags to 1.56x for one that publishes
a release for most tags, so the sum biases the score toward a publishing
workflow rather than measuring how established a project is.
**Verification Method**: Test (T)

#### L2-MET-007

**Parent**: L1-MET-002
**Statement**: Collection SHALL report the shape of the counts it found,
including when a project tags without publishing releases, when it has shipped
nothing, and when the previous definition would have reported a different
number.
**Rationale**: Two counts read together carry information neither carries
alone - 398 releases says nothing until you know whether that is most of the
tags or a handful. Reporting what the previous definition would have produced
is what makes a changed score in stored data explainable rather than
mysterious.
**Verification Method**: Test (T)

#### L2-MET-008

**Parent**: L1-MET-001
**Statement**: Every elapsed-time measurement SHALL be taken against
`scan_date`, the single instant recorded once for the run.
**Rationale**: Measuring at the moment each repository is fetched makes rows
within one file incomparable and order-dependent. On a forty-minute run the
last row's elapsed times are measured against an instant forty minutes later
than the first's, so later rows look systematically older and staler, and
re-running the same inventory in a different order changes its numbers. A fixed
anchor removes both, and because `scan_date` is a column in the row a reader
can recompute the arithmetic by hand.
**Verification Method**: Test (T)

#### L2-MET-009

**Parent**: L1-MET-002
**Statement**: An elapsed time SHALL NOT be negative, and a timestamp later
than `scan_date` SHALL be reported rather than propagated.
**Rationale**: A repository can be updated while a long scan is running, and
clocks can disagree. Either produces a negative interval, which the
implementation this replaces accepted as "just updated" and scored at full
marks. Zero is the honest value, and saying so is what turns a silent
best-possible score into something a reader can question.
**Verification Method**: Test (T)

#### L2-MET-010

**Parent**: L1-MET-001
**Statement**: Every value a row needs from the API SHALL be obtained in one
query per repository, and that query SHALL request totals only.
**Rationale**: L1-MET-001 makes cost part of correctness. One GraphQL document
returning eleven fields costs one point, so an inventory of any size fits a
5,000-point hourly budget with room to retry; the same values gathered by the
per-metric collectors cost one point each and multiply. Requesting `totalCount`
rather than `nodes` is what keeps the cost flat - a `nodes` selection prices
the query by the length of the repository's history, so the cheapest route
would quietly become the most expensive one for exactly the largest projects.
**Verification Method**: Test (T)

#### L2-MET-011

**Parent**: L1-MET-002
**Statement**: The owner and repository name GitHub reports SHALL be checked
against the values the inventory supplied, a difference SHALL be refused rather
than collected, and the `organization` column SHALL be empty when the owner is
an individual account.
**Rationale**: A repository is owned by either a user or an organisation, and
GitHub says which, so the column can state the fact rather than infer it. Empty
is the answer for a personally owned repository, not a gap - it is the only
place a row records that, and filling it with the user's login would make the
two kinds of owner indistinguishable downstream.

Refusing a moved repository is the part worth arguing for, because the
alternative looks like it works. GitHub follows a rename or a transfer
silently, so `tiangolo/fastapi` still resolves although the repository now
lives at `fastapi/fastapi`. Collecting it would produce a row in which every
number is correct, measured against a repository the inventory does not name,
with nothing in the output to say so — an error that survives review precisely
because it looks like data.

The inventory is the record of what is being measured. A reference that no
longer matches it is a defect in the list, and the honest response is to say
so and leave the measurements empty, exactly as for a repository that could not
be read at all. The current location is reported so that correcting the list is
a copy and paste rather than a search.

The name is checked as well as the owner because both redirect, and it is
asked for in the same query, so checking it costs nothing. Case is not a
difference: GitHub names are case-insensitive, and refusing a row over its
spelling would reject a working reference.
**Verification Method**: Test (T)

#### L2-MET-012

**Parent**: L1-MET-001
**Statement**: Contributor records SHALL cost at most one request per page of
accounts and one query per chunk of accounts, never one per contributor, and no
single query SHALL grow with the size of the repository.
**Rationale**: The naive route is one request per contributor, and it is the
route a library hands you by default: the REST contributors payload is a
minimal account object with no name, company or location, so reading those
completes each account lazily. Any repository of consequence would exhaust the
hourly REST budget on its own - a run that fails halfway having already spent
everything.

Aliasing accounts into a GraphQL document removes that per-contributor cost.
The condition that keeps the document cheap is the absence of a connection:
every alias selects a single object, so it carries no `nodes` and is not priced
by how many accounts could come back. That is the same condition L2-MET-002
holds the repository query to, for the same reason.

The second clause is what changed when v0.5.0 stopped truncating the list
(ADR-0006). Cost is not the constraint on a large aliased document - a chunk
costs one point whatever it carries - but GitHub terminates any query it has
not processed within ten seconds, and a document whose alias count follows the
repository is a bet against that which fails on exactly the largest inputs.
Chunking bounds the *query*, not the run.

**Verification Method**: Test (T)

#### L2-MET-013

**Parent**: L1-MET-002
**Statement**: A contributor's location SHALL be resolved to a structured
address, and the result SHALL distinguish a location that was never looked up
from one that was looked up and found nothing, and from a component the match
does not carry.
**Rationale**: Three states that a naive implementation collapses into one,
and only one of them is a measurement.

An account that publishes no location has nothing to look up. An account that
publishes `she/her` published something no gazetteer recognises, which is a
different fact about that account. A match resolved to country level genuinely
has no city, and recording that is also a fact. Collapsing them would make an
aggregate over `country` absorb all three without saying so.

Coordinates are absent rather than zero for the same reason the metric columns
are: 0,0 is a real position in the Gulf of Guinea, so a zeroed pair plots and
reads as data.

**Verification Method**: Test (T)

#### L2-MET-015

**Parent**: L1-MET-001
**Statement**: A GraphQL selection that does not resolve SHALL NOT invalidate
the selections beside it, and a failure in contributor collection SHALL NOT
end the run.
**Rationale**: GraphQL answers a partly-resolvable document with HTTP 200,
the fields it could resolve, **and** an error naming each one it could not.
Reading that as a failed query throws away correct answers; reading its
`NOT_FOUND` as "the repository is missing" misattributes it to the inventory.

Both happened. A bot login - `dependabot[bot]`, `github-actions[bot]`, a
repository's own automation - is listed as a contributor but is a `Bot` rather
than a `User`, so `user(login:)` cannot resolve it. PyGithub maps the lone
`NOT_FOUND` to `UnknownObjectException`, which was classified as a missing
repository, and the resulting `RepositoryNotFoundError` is not a
`ContributorCollectionError` - so it escaped the runner's per-repository
handling and **aborted the entire scan, producing no CSV at all**. One bot in
one repository was enough, and bots are more common in large repositories than
not.

The second clause is the general form and the more important one. The
contributor half is reached only after the repository was read successfully, so
its failures have a defined outcome already (L2-OUT-005: a row, and no
document). Any error escaping as some other type defeats that by construction,
whatever its cause.

**Verification Method**: Test (T)

#### L2-MET-014

**Parent**: L1-MET-002
**Statement**: A resolved location SHALL be remembered between runs, and a
lookup that failed for a reason unrelated to the location SHALL NOT be.
**Rationale**: Geocoding is paced at one request per second and is the slowest
part of a scan. Once the contributor list is unbounded (ADR-0006) a re-run over
a stable inventory would otherwise repeat hours of work for places that have
not moved, so what a run resolves has to outlive it.

The exclusion is the load-bearing half. A gazetteer that was unreachable,
timed out, or refused has said nothing about the location, but the address it
produces is indistinguishable from a genuine miss. Persisting that would make
one outage permanent: every later run would read "unresolved" from the cache
and never ask again, publishing an unresolved address for a place that resolves
perfectly well. That is an error that looks like data, which is the class of
defect L2-MET-011 and L2-OUT-002 exist to prevent elsewhere.

A cached answer must also be indistinguishable from a fresh one, so that no
output depends on cache state and deleting the cache costs time rather than
meaning.

**Verification Method**: Test (T)

## L2-STA: Scan statistics

#### L2-STA-001

**Parent**: L1-STA-001
**Statement**: A scan SHALL write one statistics artifact recording, per
repository, what fraction of its commits and contributors were collected and
why the remainder were not.
**Rationale**: Coverage is the difference between "87% of this project's work
is characterised" and an implied census, and the reasons are what make a gap
actionable rather than merely known. Counting a reason in **both** people and
commits is required because a reason can account for most of one and little of
the other - GitHub's email ceiling drops 88% of the people and 13% of the work,
and either figure alone misrepresents it.
**Verification Method**: Test (T)

#### L2-STA-002

**Parent**: L1-STA-001
**Statement**: The statistics artifact SHALL record the share of attributed
commits whose contributor has no resolved location, and SHALL NOT assert
anything about any person.
**Rationale**: The residency determination happens in a separate project. What
that stage needs from this one is denominators and, above all, the
unknown-location share: a national percentage computed without it implies a
precision the data has not got. Measured, one repository had 81.66% of its
attributed commits held by contributors with no resolved country, which bounds
any claim about it to within 81 points.

Publishing that bound is the whole contribution. Publishing a judgement about a
named person is out of scope here and stays out.
**Verification Method**: Test (T)

#### L2-STA-003

**Parent**: L1-STA-001
**Statement**: A figure that cannot be measured reliably SHALL be published as
`null` rather than estimated.
**Rationale**: The REST budget is the case that forced this. `/rate_limit` does
not track spend - measured at 5000 while the token had 4984 - and the accurate
response header is overwritten by any GraphQL reply, so an interleaved run
cannot read it. A plausible number there would be indistinguishable from a
measurement, which is the failure mode this project has been caught by four
times. `null` is already this package's word for "not measured".
**Verification Method**: Test (T)


## L2-SCR: Scoring

#### L2-SCR-001

**Parent**: L1-SCR-001
**Statement**: A score band table SHALL be expressed as data, SHALL be ordered
and gap-free, and SHALL map every value in its domain.
**Rationale**: An if/elif chain lets an input fall between branches, which is
exactly what happened at a count of exactly 500 in the implementation this
replaces. Expressing the bands as an ordered table makes the gap impossible by
construction, makes the table testable as one object, and lets the same
structure be rendered into the documentation rather than transcribed into it.
**Verification Method**: Test (T)

#### L2-SCR-002

**Parent**: L1-SCR-001
**Statement**: A scoring input outside its valid domain SHALL be reported and
resolved to the nearest valid value rather than scored silently.
**Rationale**: A negative count cannot arise from the API, so its appearance
means a defect upstream. Scoring it silently would let that defect travel into
the output as an ordinary number.
**Verification Method**: Test (T)
#### L2-SCR-005

**Parent**: L1-SCR-001
**Statement**: Every boundary in a band table SHALL separate two different
weights, and bounds SHALL be exact values rather than computed products.
**Rationale**: A boundary with the same weight on both sides decides nothing
while reading as though it does, and the next maintainer has to prove that
before touching it. Exactness matters for the same reason: `0.1 * 8760` is not
exactly 876 in binary floating point, and an edge that lands a fraction either
side of where it reads produces one repository in a thousand scoring
differently for no visible cause.
**Verification Method**: Test (T)

#### L2-SCR-006

**Parent**: L1-SCR-001
**Statement**: A column that scales a points budget SHALL expose the weight and
the points as separate functions.
**Rationale**: The weight is the part that is argued about and tested
exhaustively; the points budget is a single constant. Keeping them separate
lets the table be swept across its whole domain without multiplying every
expectation by a budget, and lets the budget change without touching the band
tests.
**Verification Method**: Test (T)

#### L2-SCR-007

**Parent**: L1-SCR-001
**Statement**: Where a scoring input is converted between units, the conversion
SHALL happen once and every comparison SHALL be made against the converted
value.
**Rationale**: The maturity chain converted days to years and then compared its
first threshold against the *unconverted* value, so a band meant to cover three
months covered six hours. Every repository between those two ages was scored a
band too high. A single conversion at the top of the function leaves no second
unit for a later edit to reach for.
**Verification Method**: Test (T)

#### L2-SCR-008

**Parent**: L1-SCR-001
**Statement**: A scoring function SHALL return a value on every path, and its
result SHALL be non-decreasing in the merit of its input.
**Rationale**: The fork function assigned a weight into a local and fell off
the end, returning `None` for every input and making its caller raise. Its
terminal branch also assigned 0.1 where the progression called for 1.0, so
supplying the missing return alone would have made a repository with more forks
score lower than one with fewer. Purity and totality are not enough on their
own; the direction of merit has to be checked too.
**Verification Method**: Test (T)

#### L2-SCR-009

**Parent**: L1-SCR-001
**Statement**: `total_score` SHALL be the plain sum of its components, and its
maximum SHALL be derived from their weights rather than applied as a clamp.
**Rationale**: The weighting has already happened by the time the components
exist: each is `weight x points` with a weight of at most 1.0, so each is capped
by construction and the total is capped by their sum. Writing the maximum down
as a clamp would hide the case it exists to catch — a component that has
drifted past its own share would still produce a total reading 85.0, with
nothing to say which one. A ceiling that is also a sum cannot hide it: the
total either overshoots or fails to reach 85.0, and the overshoot is reported
with the offending component named rather than being flattened away.
**Verification Method**: Test (T)

## L2-TRU: Trust policy

#### L2-TRU-001

**Parent**: L1-TRU-001
**Statement**: Owner matching SHALL be case-insensitive and insensitive to
surrounding whitespace.
**Rationale**: GitHub account names are case-insensitive, so `Google` and
`google` address the same organisation. An inventory maintained by hand will
contain both spellings, and a trust decision that depended on which one was
typed would be indefensible.
**Verification Method**: Test (T)

#### L2-TRU-002

**Parent**: L1-TRU-001
**Statement**: The registry SHALL record the institution behind each trusted
owner, not merely that the owner is trusted.
**Rationale**: The institution is the substance of the judgement and is not
recoverable from anywhere else. Keeping only a boolean would discard the reason
the owner was listed, leaving a later maintainer unable to review the policy.
**Verification Method**: Test (T)

#### L2-TRU-003

**Parent**: L1-TRU-001
**Statement**: The default list SHALL be immutable, and a caller SHALL be able
to supply its own.
**Rationale**: A mutable module-level default lets one run's edit leak into the
next within the same process, which matters once this package is embedded in a
longer-running program. Accepting an explicit mapping is what makes the policy
replaceable ahead of a configuration source existing.
**Verification Method**: Test (T)
#### L2-TRU-004

**Parent**: L1-TRU-001
**Statement**: The trusted-organisation bonus SHALL be a flat award, resolved
through the same registry as the `is_trusted_org` column.
**Rationale**: Every other component scales a points budget by a 0.0-1.0 weight
because its input is a count that varies. Trust is a yes-or-no judgement, so
there is nothing for a weight to interpolate between and a band table would be
a table of two rows. Resolving both the column and the bonus through one
registry means there is a single answer to "is this owner trusted" rather than
two that can drift apart.
**Verification Method**: Test (T)

## L2-CFG: Credentials

#### L2-CFG-001

**Parent**: L1-CFG-001
**Statement**: A token supplied explicitly SHALL take precedence over the
environment, and a blank explicit value SHALL fall back to it.
**Rationale**: An explicit argument beats ambient configuration, so an operator
can override a stale `.env` without editing it. Treating a blank flag as an
override rather than a fallback would turn an empty shell variable into an
authentication failure with no useful message.
**Verification Method**: Test (T)

#### L2-CFG-002

**Parent**: L1-CFG-001
**Statement**: Credentials SHALL be verified through an endpoint that does not
consume the rate limit.
**Rationale**: A check that costs a request taxes every run for the benefit of
the rare bad-token run. `GET /rate_limit` is exempt from the rate limit -
measured directly, core remaining was 5000 before the call and 5000 after - and
answers 401 for a token that is not valid, so the check is both free and
definitive. It also returns the OAuth scopes, so one call reports validity and
permissions together.
**Verification Method**: Test (T)

#### L2-CFG-003

**Parent**: L1-CFG-001
**Statement**: A missing credential and a rejected credential SHALL carry
distinct codes and distinct exit statuses.
**Rationale**: The fixes differ. One means "configure a token"; the other means
"the token you configured no longer works". Collapsing them would leave an
operator, and a pipeline, unable to tell which.
**Verification Method**: Test (T)

#### L2-CFG-004

**Parent**: L1-CFG-002
**Statement**: Diagnostics SHALL report the token's source, kind, length, and
the scopes GitHub reports, and SHALL NOT report the token.
**Rationale**: These four answer every question a credential failure raises -
which token, from where, of what type, with what permissions - and none of them
is the secret. The prefix identifies the token's *type*, which is public
information about its shape rather than about its material.
**Verification Method**: Test (T)

#### L2-CFG-005

**Parent**: L1-CFG-001
**Statement**: A token SHALL be accepted by path as well as by value, and
supplying both forms SHALL be a usage error.
**Rationale**: L1-CFG-001 requires a command-line route for credentials, and
the obvious one puts the secret in the process listing and the shell history. A
path is not a secret, so `--token-file` gives the same reach with nothing
disclosed, and it is the shape a mounted container secret already has.
Surrounding whitespace is stripped because a file written by `echo` ends in a
newline and GitHub answers a trailing newline with the same 401 as an expired
token - a failure that reads as the wrong problem.

Both forms together is refused rather than resolved by precedence: it can only
be a mistake, and choosing one would mean silently ignoring a credential the
operator deliberately supplied.
**Verification Method**: Test (T)
